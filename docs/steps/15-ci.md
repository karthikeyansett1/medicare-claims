# Step 15 — Reproducible CI and Docker builds

## What changed and why

GitHub Actions now builds the warehouse against a fresh PostgreSQL 16 service on every push and pull request. The `ci` job installs the locked Python 3.11 requirements, loads a committed synthetic fixture, runs dbt, fits the expected-cost model, builds the dependent metrics, generates comparisons and public dashboard exports, runs independent reconciliation, lints SQL, and runs the Python suite including database permission checks. It never calls an LLM or requires an API key. Paid evaluation remains deferred.

The fixture contains exactly 1,000 Sample 1 members. A purely random 1,000-member subset rarely preserves reportable provider panels. To test the existing 20-member threshold and ten-provider deciles without weakening production rules, the fixture uses 490 fixed anchors and 510 additional members selected with seed 15 from the sorted remaining population. The anchors are 25 eligible members from each of the ten largest shared A/B provider panels in each performance year (ties by NPI), selected with seed 15. Cross-year overlap leaves 490 distinct anchored members. `anchors.json` records the IDs and groups. This is an intentionally stratified engineering fixture, not a representative statistical sample.

All source rows for the selected IDs are retained. IDs, dates, values, CSV headers, and physical source lines are unchanged. Deterministic gzip (empty filename, timestamp zero) keeps the committed fixture directory at **4,151,256 bytes**, below 10 MB; extraction occurs only inside an ignored or external runtime directory. `fixture.json` records source and fixture SHA-256 hashes, expected row counts, and the selected member IDs. Full CMS expected counts remain separate reference metadata in the profile; fixture expected counts do not replace them. Profiling, streaming COPY hash checks, exact integer-cent financial reconciliation, and dbt uniqueness/relationship tests still run.

## Reproduce

For the complete Samples 1 and 2 warehouse, configure `.env` using `.env.example`, install Docker and either uv or Python 3.11, then run:

```sh
make all
```

`all` runs setup, starts the full database, downloads/profiles the selected samples, loads bronze, installs dbt packages, builds upstream models, fits risk adjustment, builds dependent metrics, compares methods, and exports. Full-data sample default remains `1,2`. Database stages use sequential recursive Make recipes, including under `make -j`; `.env` is parsed by python-dotenv and never sourced as shell or Make code.

For a fresh fixture pipeline, use the dedicated Compose file and a new project name:

```sh
docker compose --env-file /dev/null -p medicare-fixture-ci \
  -f compose.ci.yml up --build --abort-on-container-exit --exit-code-from pipeline
```

This starts its own PostgreSQL cluster and `fixture_pgdata` volume without publishing a host port. The pipeline uses the Compose service hostname `db`. It cannot connect to the full warehouse's volume. The credentials in this file are disposable test credentials. `.dockerignore` excludes local credentials, gigabytes of raw/extracted data, virtual environments, Git metadata, and generated caches. The image uses native architecture and the same requirements lock on ARM64 and AMD64.

To repeat this exact fixture project from zero, remove only that explicitly named disposable project:

```sh
docker compose --env-file /dev/null -p medicare-fixture-ci -f compose.ci.yml down -v
```

Never run `down -v` against the full warehouse project. A different new project name also provides a fresh database without deleting anything.

To run on an independently provisioned empty PostgreSQL cluster (the approach used by Actions):

```sh
PG_HOST=localhost PG_PORT=55432 PG_USER=medicare PG_PASSWORD=ci_password \
PG_DB=medicare_ci ASSISTANT_PG_PASSWORD=ci_readonly_password \
DATA_DIR=data/fixtures OUTPUT_ROOT=/tmp/medicare-ci-run make ci
```

Install locked dependencies first (`make setup` with those same database environment variables, or `pip install -r requirements.txt` in a Python 3.11 environment). Choose an empty output directory. `DATA_DIR` points to the compressed fixture package; the runtime materializes verified CSVs under its own `data/extracted/sample_1`, and the ordinary loader consumes that override. Reproduce the committed archives from the acquired full Sample 1 sources with `python -m ingest.make_fixture`.

## Isolation and validation

Fixture execution copies project files into `OUTPUT_ROOT`, excluding `.env`, raw data, virtual environments, and caches. Every generated profile, verification report, risk-model diagnostic, comparison chart/CSV, and dashboard export stays in that runtime. Output roots cannot replace the source checkout or existing evidence, and symlink inputs are rejected. Before database writes, the runtime validates archive/content hashes, exact source headers, row counts, member cohort, and eight-file Sample 1 identity.

The internal pipeline requires the isolated-runtime marker and explicit database settings with a `_ci` database name. It refuses clusters with another user database, application objects, or an existing `assistant_ro` role. A database-name suffix alone is insufficient because PostgreSQL roles are cluster-global; resetting the read-only role in another database of the full cluster would still break the full warehouse. These checks deliberately require a fresh dedicated cluster. Fixture profiles cannot be passed to the ordinary loader outside the isolated runtime. The runtime clears inherited Make overrides and fixes the selected sample to 1.

The assistant integration tests still execute all eight original SQL examples. For examples scoped to Sample 2, fixture mode also executes a Sample 1 equivalent and asserts a nonempty result; an empty original Sample 2 result is correct when that sample is not loaded. No production SQL examples or full-data gold answers are rewritten.

## Evidence and limits

The fresh tracked-file snapshot is `/tmp/medicare-step15-fresh`; local secrets and ignored raw data were absent. The isolated Docker log is `/tmp/step15-fresh-docker.log`. The core dbt build passed 154 nodes with three expected data-quality monitor warnings; dependent metrics passed ten nodes with no errors. Independent metrics verification covered 40 reportable panels, ten for each method/year, and comparison verification covered 215 provider pairs and 30 aggregate comparisons. The fixture includes 688 readmission episodes.

The local non-database suite passed 114 tests, with 19 opt-in database tests skipped. Fresh Docker completed with **exit code 0 and all 133 Python tests passing**, including database permission and rollback tests; SQL lint also passed. The original full warehouse still contains **23,004,945 raw rows**; all five table counts and assistant role settings match the pre-run snapshot, and its original read-only credential still authenticates. All 119 pre-existing protected evidence files are byte-identical (the separately tracked roadmap was intentionally updated). See [machine-readable verification](15-ci-verification.json). Runtime evidence was copied to `/tmp/step15-runtime-evidence`. Local success does not establish GitHub Actions success: the first pushed PR must show the actual `ci` job green before making it a required branch check. No branch-protection or merge claim is made here.

## Interview explanation

“The difficult part was preserving production behavior while making CI small. I kept all eight source schemas and all rows for 1,000 selected synthetic members, compressed the fixture below 10 MB, and deliberately preserved enough provider panels to test the real reporting thresholds. CI refits the risk model before building its dependent mart and independently reconciles counts and money. I also isolated both the database cluster and generated evidence, because a fixture run must not overwrite full-data findings or reset the full warehouse's PostgreSQL role.”
